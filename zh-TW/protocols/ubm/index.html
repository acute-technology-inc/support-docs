    UBM (Universal Backplane Management, SFF-TA-1005)

    UBM 是 SNIA 在 SFF-TA-1005 定義的儲存背板管理介面。主機透過一條 兩線式側帶（SCL 與 SDA）向背板上的 UBM Controller 查詢每一個 DFC（Drive Facing Connector）的狀態：硬碟在不在、是 SAS 還是 PCIe、電源與 PERST# 怎麼管、狀態 LED 怎麼亮。

    這條側帶上會同時出現三種裝置，而只有第一種的位址是規格固定的：

    裝置 位址 出處
    UBM FRU（存放背板描述的 EEPROM） 寫 AEh、讀 AFh §3
    2Wire Mux E0h–EFh §4.5
    UBM Controller 不固定 —— 由背板廠自行決定，並記錄在 FRU 裡 §5.3.2.2.1

    規格另外定義了兩種訊框格式，而且它們是兩個協定，不是同一個協定的變體。§5.1 的 FRU 存取是 一般的 EEPROM 交易，沒有交易檢查碼；§6.1 的 Controller 命令則在寫入帶一個命令檢查碼、 在回覆帶一個讀取檢查碼。

    解碼設定

    設定 作用 預設
    SCL、SDA §4.1 Table 4-1 的兩條側帶訊號，兩條都是必要的。UBM 沒有相位選項，因為 2Wire 沒有 CPOL/CPHA 的概念。 CH 0、CH 1
    檢視 這個標籤要顯示哪一層。Transaction 是一列一筆 UBM 交易；Field 是一列一個具名欄位。它選的是顯示哪一層，不是解碼哪一層 —— 想同時看兩層，就加入兩次解碼、各選一個檢視。 Transaction
    從 UBM FRU 學習控制器位址 讀取擷取檔裡的 FRU 內容，循 IPMI 的記錄鏈找到 Overview Area，從中取出 UBM Controller 的位址。報表表頭會說明這次用的是哪一個來源。 勾選
    控制器位址 當擷取檔裡沒有 FRU 讀取時，指定要視為 UBM Controller 的 8-bit 位址。勾選後才能輸入，而且會蓋過學習到的值。 未勾選
    標示超出規格的存取 當實測的 SCL 速率高於 400 kHz 時，在報表表頭多加一列。400 kHz 是 Appendix C 第 1 條裡 UBM Controller 的速率，而那一條是 informative：SFF-TA-1005 從頭到尾沒有規定匯流排速率，所以跑得更快只是超出 UBM 設計時假設的範圍，並不是違反要求。因此它永遠是一則說明、不是錯誤，那條匯流排上的流量也可能完全正常。 勾選
    顯示 I2C 匯流排層 在波形區把底層的傳輸也畫出來 —— START、Repeated START、acknowledge、STOP —— 與 UBM 的方塊並存。 勾選
    波形顏色 Start/Stop、Target、Read、Command、Data、Field、Value 各一個色票。檢查碼的判定不在這裡：它固定是通過綠、失敗紅，這樣判定就不可能被設定成看不見。 依協定
    分析範圍 要解碼緩衝區的哪一段。 緩衝區開頭 → 緩衝區結尾

    解碼結果

    每一份報表都是先講量到了什麼，再講是怎麼讀的：

    列 範例 這一列在講什麼
    1 SCL Clock: 101.8 kHz (measured) 從擷取檔自己的邊緣量出來的時脈頻率 —— 不是任何設定裡的數字。「匯流排實際速率和預期不同」是解碼看起來不對時最常見的原因，而這一列就是它現形的地方。not detected - no complete byte 表示這份擷取檔裡沒有一個被 acknowledge 的位元組可以量。
    2 View: Transaction / Flag out-of-spec accesses 底下那些列是用哪一個檢視建出來的，以及有開著的非預設選項。同一份擷取檔用兩個檢視各出一份報表，少了這一列在紙上就分不出來。
    接著 UBM Controller address learned from the UBM FRU UBM Controller 的位址從哪裡來 —— 「UBM Controller C0」這句話，在「從 FRU 讀到的」和「使用者打進去的」兩種情況下意義不同。

    表頭之後的列只在成立時才出現：FRU 表頭檢查碼失敗、Field 檢視沒有東西可顯示，以及下面講的 2Wire Mux 說明。

    Transaction 檢視一列一筆 UBM 交易，欄位是 Target、R/W、Command、Len、 Data、Checksum、Error 與 Information。一次 Controller 讀取在匯流排上是兩個相位 —— 先寫入命令、Repeated START、再讀出 —— 各自成為一列，因為兩個相位各有自己的位址與檢查碼。

    Field 檢視一列一個具名欄位，欄位是 Command、Field 與 Value。33h Capabilities 那兩個 byte 會變成十一列：35h 05h 本身什麼都沒說，而 2WIRE_RESET# Operation = 3h Slave Reset + FRU + Controller + Mux 說出了這塊背板能做什麼。 這個檢視的 Target 與 R/W 刻意留白 —— 它的主題是那些位元代表什麼意思，而位址在另一個 檢視的每一列上都有。

    DFC Status and Control Descriptor，以及裡面那個 SES-4 元素

    40h DFC Status and Control Descriptor 是操作者通常真正想看的那一筆：這個槽位插了什麼、 機箱對它的說法是什麼。它的前兩個 byte 是 UBM 自己的欄位（Drive Type Installed、 Bifurcate Port、PCIe Reset、DFC Change Count），而後四個 byte 是一個原封不動的 SES-4 Array Device Slot 元素。SFF-TA-1005 沒有重寫那些位元的定義，而是指向 SES-4， 所以解碼也照 SES-4（Table 74）讀它們。

    Field 檢視把它們全部命名，而那正是「八個十六進位數字」與「一個答案」之間的差別：

    欄位 它告訴你什麼
    SES Element Status Code 這個槽位的總體裁決，同時給代碼與名稱 —— 2h Critical 與 5h Not Installed 當成數字看很像，意思卻完全不同
    SES IDENT、SES FAULT REQSTD、SES FAULT SENSED 機箱要求點亮哪一個指示燈、以及它自己認定的狀態 —— 「LED 亮錯顆」就是在這裡看出來的
    SES REBUILD/REMAP、SES IN CRIT ARRAY、SES IN FAILED ARRAY 陣列認為這個槽位正在做什麼
    SES DO NOT REMOVE、SES APP CLIENT BYPASSED A/B、SES HOT SPARE 一個看起來健康的槽位為什麼沒有被使用

    沒有這個檢視，那四個 byte 就只是兩欄十六進位；而 UBM 這條匯流排存在的目的之一 —— 承載 LED 與故障指示 —— 就完全無法從擷取檔裡讀出來。

    同一個檢視也會讀 UBM FRU 自己的內容。FRU 存取沒有命令位元組，所以 Command 欄顯示的是這個 欄位屬於哪一個區塊 —— FRU Common Header、FRU MultiRecord Header、UBM Overview Area 或 UBM Port Route Info Descriptor —— 而不是命令。

    每個區塊從哪裡開始，是從 FRU 自己讀出來的：Common Header 給出 MultiRecord 區的偏移， 每筆記錄的長度給出下一筆從哪裡開始。解碼會跨擷取檔裡所有的 FRU 讀取去走這條鏈， 所以不論 host 是一次讀完還是分批讀，結果都一樣 —— Appendix C 第 2 條建議分 8 × 32 byte 讀， 所以一個 7 byte 的 route descriptor 常常是被切在兩筆交易裡的。

    存的數字不等於它名字所指的那些欄位會被展開，因為那正是這個檢視的價值所在： Link Width 0h 是1 條 lane、Maximum Power 0 是沒有上限、區塊偏移 1 是 byte 8、 DFC index FFh 表示這裡沒有接 DFC，而 UBM FRU Invalid = 0 表示 FRU 是有效的。

    只有真的擷取到的位元組才會被報告。 一份只含 FRU 前八個位元組的擷取檔，只會得到 Common Header，再往後什麼都沒有 —— 因為再往後的每一個偏移與長度，都要從不在手上的位元組 裡讀出來，所以不替它們假設任何值。

    SFF-TA-1005 R1.3 標為 Reserved 的 Overview Area 位元組不會被命名，即使至少有一家廠商的 實作在那裡定義了欄位。

    SCL 與 SDA 接反的時候

    兩支探棒接反的 2Wire 擷取檔會什麼都解不出來：時脈的邊沿跑到資料線上，所以一個 byte 都 框不出來。解碼不會幫你對調回來 —— 它會講出來，並且點名要改哪裡：

    SCL Clock: not detected - no complete byte
SCL and SDA may be swapped - SDA carries far more edges than SCL
No byte was decoded - exchange SCL and SDA in the Channel setting

    到「解碼設定」對話框的 通道設定 群組裡，把兩個選擇器對調即可。探棒很可能插在對的腳位上， 只是對話框裡兩個通道指反了。

    這個註記只會出現在「完全沒有解出任何 byte」的擷取檔上，而且還要資料線的邊沿數超過 時脈線的兩倍。正常匯流排上 SCL 每個 bit 翻兩次、SDA 最多翻一次，所以有解出東西的擷取檔 不可能出現這個訊息。完全沒有訊號的擷取檔也不會出現：用寥寥幾個邊沿算出來的比值毫無意義， 所以邊沿數不到 64 個時，解碼寧可不說話也不猜。

    歸屬不到的 2Wire Mux 通道

    §4.5 把 mux 的通道選擇放在另外一筆、更早的交易裡。當那一筆不在解碼範圍內 —— 範圍被設成從 中間開始，或者錄製本身就是從後面才開始 —— 第一筆 mux 寫入之前的那段流量，屬於更早選到的那個 通道，而那是無法從匯流排上得知的。報表會把這件事講出來，而不是讓人去猜：

    2Wire Mux channel is unknown - the channel select is outside the window

    它只在範圍內有 mux 回應過自己的位址時才出現，因為那是「這條線上真的有 mux」唯一的證據。 對 mux 位址的寫入如果沒有人 acknowledge，那是 host 在探測 mux 而且沒找到，不列入計算。第一筆 mux 寫入之前的 FRU 存取也不會觸發：§4.5 禁止把 UBM FRU 放在 2Wire Mux 後面，所以 FRU 的流量 從來沒有疑義。

    位址一律以 8 位元呈現

    SFF-TA-1005 全部以八位元寫位址、含 R/W# 位元 —— FRU 是 AEh 與 AFh、mux 是 E0h–EFh —— 所以這個解碼器也照著做，波形區的 Target 方塊涵蓋整個位址位元組。同一份擷取檔用 I2C 解碼會 顯示 7 位元的形式，所以同一個裝置在那裡是 57h、在這裡是 AEh/AFh。那是同一個位址： AEh = 57h << 1。

    這也是為什麼一筆交易會出現兩個 Target。AEh/C0h 是寫入相位、AFh/C1h 是讀取相位， 是同一個裝置，不是兩個。

    FRU 存取的 Checksum 欄是空的

    §5.1 寫明 FRU 的內容是由內容結構自己的檢查碼保護的，所以 FRU 交易本身沒有檢查碼。 那幾列的 Checksum 欄因此刻意留空，Information 欄會說明原因。在那裡套用 §6.1 的規則， 會讓每一次 FRU 讀取都被判成失敗。

    Error 與 Information

    訊息 意義
    UBM Controller address learned from the UBM FRU 位址是從這份擷取檔的 FRU 內容讀出來的。
    UBM Controller address taken from the settings 位址來自控制器位址欄。
    No UBM Controller address known - UBM layer not decoded 兩個來源都沒有。Controller 的流量會被報成 Non-UBM。
    UBM FRU access - the FRU protocol carries no transaction checksum 見上，不是故障。
    UBM FRU header checksum failed - the FRU content is unreliable and no controller address was taken from it IPMI 共用表頭的總和不為零。解碼器拒絕從信不過的內容學習位址。它不指明是哪一方的問題 —— 內容檢查碼不過，說不出是 EEPROM 存了壞資料、還是擷取把好資料讀錯了；在訊號品質邊緣的錄製上，後者才是比較可能的那一個。
    Capture ended before the transaction completed 擷取視窗在交易中途結束。這是錄製的性質，不是匯流排出錯，所以它放在 Information 而不是 Error。
    Command code is not defined in SFF-TA-1005 Rev 1.3 命令碼不在 Table 6-6 裡。
    Checksum does not match §6.1 的命令或讀取檢查碼失敗。這一個才是 Error。
    All bytes FFh - the controller reports an invalid command or checksum §6.1 Table 6-5：UBM Controller 偵測到無效命令或無效命令檢查碼時，會把讀取的每一個 byte 都填成 FFh —— 包含 Read Checksum。這一列和上面那個檢查碼 Error 同時出現，而兩者說的是不同的事：Error 說「位元組加起來不對」，這一列說「這個樣式代表什麼」。檢查碼在這裡本來就該失敗，host 就是靠它發現的。所以要去查的是 host 送了什麼，不是訊號品質。

    說明事項

    • UBM Controller 的位址不是規格固定的。 §5.3.2.2.1 把它留給背板廠，並記錄在 FRU 裡。 如果擷取檔裡沒有 FRU 讀取，請在設定裡填入位址 —— 否則 Controller 的流量會被報成 Non-UBM，那是解碼器在表示「我沒有依據把它叫成別的」。

    • Data 欄每列 16 個 byte，所以整份 FRU 映像會呈現成數列 × 16，與 IPMI 的結構對齊。

    • Live mode 的解碼結果與 offline 相同，但有四項明文限制。 live 期間報表與波形區都帶 UBM 層，而且文字與停止擷取後逐組相同。live 做不到的是：

      1. 一筆交易只判定一次，不會回頭重判。 它在自己的 STOP 到達時發布，而發布是最終的。 所以出現在「命名控制器的那筆 FRU 讀取」之前的控制器流量會留在 Non-UBM， 而停止擷取後重讀記錄會把它改判成 UBM Controller。報表表頭每一場 live 都會講這件事。
      2. 報表表頭在任何流量到達之前就寫出去，所以它陳述的是「當下已知的狀態」 —— 尤其是位址來源 —— 而不是整份擷取完成後才知道的事。
      3. 不量 SCL 速率，所以第一列是 not measured during a live session。
      4. 還在進行中的那一筆交易要等停止擷取才出現，因為它的檢查碼判定與位元組角色 都還不可能知道。

    • 這條匯流排的擷取品質很重要。 背板側帶上常有 SCL 的短毛刺，而落在時脈邊緣的毛刺會改變 一個位元組的起點。解碼結果與匯流排應有的行為不符時，請開啟軟體突波過濾。
